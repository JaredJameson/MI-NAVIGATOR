export function formatRelativeTime(dateString: string, locale: string = 'pl-PL'): string {
  const date = new Date(dateString);
  const now = new Date();
  const diffMs = now.getTime() - date.getTime();
  const diffSec = Math.floor(diffMs / 1000);
  const diffMin = Math.floor(diffSec / 60);
  const diffHour = Math.floor(diffMin / 60);
  const diffDay = Math.floor(diffHour / 24);

  if (diffSec < 60) {
    return locale === 'pl-PL' ? 'przed chwilą' : 'just now';
  } else if (diffMin < 60) {
    return locale === 'pl-PL'
      ? `${diffMin} ${diffMin === 1 ? 'minuta' : 'minut'} temu`
      : `${diffMin} minute${diffMin > 1 ? 's' : ''} ago`;
  } else if (diffHour < 24) {
    return locale === 'pl-PL'
      ? `${diffHour} ${diffHour === 1 ? 'godzina' : diffHour < 5 ? 'godziny' : 'godzin'} temu`
      : `${diffHour} hour${diffHour > 1 ? 's' : ''} ago`;
  } else if (diffDay < 7) {
    return locale === 'pl-PL'
      ? `${diffDay} ${diffDay === 1 ? 'dzień' : 'dni'} temu`
      : `${diffDay} day${diffDay > 1 ? 's' : ''} ago`;
  } else {
    // Fall back to formatted date for older dates
    return formatDateInTimezone(dateString, 'Europe/Warsaw', locale);
  }
}

### Bug: Missing Field in Response Schema

**Problem Pattern:**
When a field is saved to database but not returned in API response, frontend will lose that data on page reload.

**Detection:**
1. Field saves successfully (POST/PUT works)
2. Field stored in database correctly
3. But GET endpoint doesn't return the field
4. Frontend displays default/empty value after reload

**Solution:**
Ensure response schemas match database model:
- ✅ Add field to Pydantic response model
- ✅ Include field in endpoint return statement
- ✅ Set appropriate default value
- ✅ Test full save/load cycle

### Response Schema Completeness Checklist

When adding new user preferences:
1. ✅ Add field to database model
2. ✅ Create migration
3. ✅ Add to UPDATE request schema (UserPreferencesUpdate)
4. ✅ Add to UPDATE response schema (UserPreferencesResponse)
5. ✅ Add to PROFILE response schema (UserProfileResponse) ← **Often forgotten!**
6. ✅ Include in GET endpoint response
7. ✅ Include in PUT endpoint response
8. ✅ Set appropriate default value
9. ✅ Test save/load cycle

### Testing Strategy for Persistence Features

**Comprehensive test must cover:**
1. **Save** - POST/PUT with new values
2. **Verify immediate response** - Check API returns saved values
3. **Load** - GET to fetch data (simulates page reload)
4. **Verify persistence** - Compare loaded vs saved values
5. **Test all fields** - Don't assume one working means all work

**Good test script structure:**
```bash
# 1. Setup (create user, login, get tokens)
# 2. Save data with specific test values
# 3. Fetch data (simulate reload)
# 4. Assert each field individually
# 5. Report results clearly
```

### Dropdown Persistence Requirements

For dropdown persistence to work:
1. ✅ Frontend state management (useState, useEffect)
2. ✅ Load data on mount (fetchProfile)
3. ✅ Save data to API (handleSave)
4. ✅ Backend validates and stores
5. ✅ Backend returns updated data ← **Critical!**
6. ✅ Frontend updates state with response
7. ✅ Database persists correctly
8. ✅ GET endpoint returns all fields

**Common Pitfall:**
Saving works, database has data, but GET doesn't return it → appears as if persistence is broken.
