## TECHNICAL INSIGHTS

### Authentication Architecture Discovery

**Key Finding:** Application uses **localStorage** for auth, not cookies!

**Storage Structure:**
```javascript
localStorage:
  - mi_navigator_token: JWT access token
  - mi_navigator_refresh_token: JWT refresh token
  - mi_navigator_csrf_token: CSRF protection token
```

**Impact:**
- All authenticated requests must include Authorization header
- Cannot rely on `credentials: 'include'` alone
- Need to read token from localStorage for every request

**Why This Matters:**
- Previous assumption: auth via cookies
- Reality: JWT tokens in localStorage
- This explains why onboarding was failing (no token sent)

### API Proxy Pattern

**Current Setup:**
```
Frontend → /api/proxy/* → Next.js Proxy → http://localhost:8004/api/v1/*
```

**Benefits:**
- Avoids CSP violations
- Works with Playwright MCP browser
- Single origin for frontend and API
- Proxy forwards Authorization headers

**Configuration:**
- Frontend: `NEXT_PUBLIC_API_URL=http://localhost:3000/api/proxy`
- Backend: `BACKEND_API_URL=http://localhost:8004/api/v1`
- Proxy: `/frontend/src/app/api/proxy/[...path]/route.ts`

### Data Consistency Issue

**Problem:** Onboarding and settings use different role values

**Onboarding (BEFORE FIX):**
```typescript
{ id: 'strategy', name: 'Strategy / Business Development' }
```

**Settings:**
```typescript
{ value: 'bd', label: 'Business Development' }
```

**Result:** Data saved as 'strategy' but no matching dropdown option

**Fix:** Aligned onboarding to use 'bd' value

**Lesson:** Always check data consistency across forms!
