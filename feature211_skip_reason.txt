# Feature #211 - SKIPOWANA - Wymaga Pełnej Implementacji

## Data: 2026-01-19 - Session 255

## Powód Pominięcia

Feature #211 (Usage limit enforcement) wymaga pełnej implementacji systemu enforcement limitów użytkowania, którego obecnie BRAK w aplikacji.

## Analiza Stanu Obecnego

### ✅ CO ISTNIEJE:
1. **Dashboard pokazuje limity**
   - Wyświetla "0/100 analyses this month"
   - Endpoint: GET /api/v1/users/usage
   - Kod: backend/app/api/v1/endpoints/users.py (linie 605-634)

2. **Limity zdefiniowane:**
   - User role: 100 analiz/miesiąc
   - Admin role: 1000 analiz/miesiąc
   - Storage limits: 10GB (user) / 100GB (admin)

3. **Rate Limiting dla API:**
   - Middleware: backend/app/core/rate_limit.py
   - Limit: 10000 requestów/miesiąc
   - Zwraca 429 gdy przekroczony

### ❌ CO BRAKUJE (ENFORCEMENT):
1. **Brak sprawdzenia przed akcją:**
   - Chat endpoint (/api/v1/chat) - brak sprawdzenia
   - Research endpoint (/api/v1/research) - brak sprawdzenia
   - Analysis endpoint (/api/v1/analysis) - brak sprawdzenia

2. **Brak blokowania akcji:**
   - Użytkownik może zrobić 101, 200, 1000 analiz
   - Nie ma sprawdzenia przed utworzeniem nowej analizy

3. **Brak komunikatów błędów:**
   - Nie ma HTTP 403 "Limit exceeded"
   - Nie ma przyjaznego komunikatu dla użytkownika

## Zakres Implementacji (Oszacowanie 4-6h)

### Backend:
1. Dodać funkcję `check_usage_limit(user_id, action_type)` w core/
2. Dodać decorator `@enforce_usage_limit` dla endpointów
3. Dodać sprawdzenie w:
   - `/api/v1/chat` (WebSocket + REST)
   - `/api/v1/research`  
   - `/api/v1/analysis`
4. Dodać HTTP 403 exception z przyjaznym komunikatem
5. Testy jednostkowe dla enforcement

### Frontend:
1. Obsługa błędu 403 w chat/research/analysis
2. Modal z komunikatem "Usage limit exceeded"
3. Link do upgrade/billing page
4. Wizualna warning gdy blisko limitu (90%+)

### Database:
- Może wymagać dodania tabeli usage_tracking dla dokładnego liczenia
